# Hackathon: your steps

**Google plans once. Qoder implements continuously. You verify and submit.**

1. **Read the brief/rubric.** Confirm the deadline, required stack and submission
   rules. Give both permitted tools the originals, including the complete rubric
   PDF. Check that every page/table is readable.
2. **Get the plan from Google.** Use [playbook prompt A](HACKATHON-PLAYBOOK.md#a-google-plan-once)
   with the originals and actual starter facts: file tree, dependency manifest,
   scripts and relevant code. Say if there is no starter. Answer essential
   questions; use B only if the plan has gaps.
3. **Check coverage and save once.** Ensure every full-mark criterion maps to an
   implementation/check step. Save Google's execution plan as `EXECUTION-PLAN.md`
   in the assessment project. Keep its checklist in chat or your own notes;
   a separate status document is optional.
4. **Start Qoder.** Attach/reference the original brief, rubric PDF, plan and
   [short rules](QODER-HACKATHON-RULES.md). Send prompt C. Do not load this whole
   playbook into Qoder. Let it work through related steps without stopping for
   a new prompt after each task.
5. **Monitor working milestones.** Try the app, inspect changes and save working
   Git checkpoints. Run routine checks yourself where practical. Check credits;
   preserve **600 for late blockers**. Start with Efficient if it still shows
   0.0x; use Auto if it struggles. Fast replaces the old Performance tier.
6. **Handle persistent blockers.** Qoder can fix straightforward local errors.
   After repeated failures or a required design change, give Google D with the
   exact error, current relevant code and attempts made. Apply the focused fix.
7. **Check every criterion before submitting.** Qoder's final evidence table is
   **in chat only**. Use E only if it has not already provided that audit. Copy
   the response to Google with F; send only the resulting gaps back to Qoder.
   You may save the chat response yourself. Do not pay Qoder to duplicate it.
8. **Submit with a buffer.** Start final review around hour 6; reserve the last
   45 minutes for submission and blockers. Run required checks, follow the app's
   run instructions in a fresh copy and verify the actual submission. Verify the
   remote commit if Git delivery is required.

Keep prepared materials within the exam's rules. Target every full-mark
requirement with real evidence; neither AI can guarantee the lecturer's score.
`this_is_a_test.md` is an older guide; use the new brief's timing and rules.
